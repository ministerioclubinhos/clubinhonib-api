# Error Handling System - Clubinhos NIB API

Photo/video comment endpoints reuse the existing error catalog; their exact access,
validation and conflict conditions are documented in
[Feed photo comments — Errors](feed-photo-comments.md#errors).

Rejection without a trimmed 1–500 character reason returns 400
`VALIDATION_ERROR`; repeated/stale decisions return 409 `RESOURCE_CONFLICT`.
Reading a missing or foreign notification returns 404 `RESOURCE_NOT_FOUND`.
Inbox listing and acknowledgment enforce account activity and the feed flag.
Email errors are logged without rolling back the decision or private notice.

## Overview

The API uses a standardized error handling system with specific codes and a consistent response format.

## Error Response Format

All error responses follow this format:

```json
{
  "success": false,
  "error": {
    "code": "USER_2001",
    "message": "User not found", // Human-readable message (in Portuguese for end-users)
    "details": null,
    "timestamp": "2024-01-15T10:30:00.000Z",
    "path": "/api/users/123"
  }
}
```

### Fields

| Field | Type | Description |
|-------|------|-----------|
| `success` | boolean | Always `false` for errors |
| `error.code` | string | Unique error code (see table below) |
| `error.message` | string | Friendly message in Portuguese (localized for UI) |
| `error.details` | any | Additional details (validation errors, specific fields, etc.) |
| `error.timestamp` | string | Error timestamp (ISO 8601) |
| `error.path` | string | Endpoint that generated the error |

### Correlation ID

Every response carries an `X-Request-Id` header with a UUID generated by the
server (`RequestContextMiddleware`). The same value is stored as `requestId`
in the audit event of the request and in any technical record written while
handling it, so an error reported by a user can be traced with
`GET /log-records/audit?requestId=...` and
`GET /log-records/observability?requestId=...`. Client-provided request ids
are ignored. The error envelope itself is unchanged. See
[`observability-audit.md`](observability-audit.md).

### Capture

`GlobalExceptionFilter` is registered through `APP_FILTER` (not instantiated
in `main.ts`) so it can close the request in the execution context: it sets
status and error code, records the audit outcome once, and logs `5xx` through
`Logger.error` — which the structured logger persists — and `4xx` through
`Logger.warn` (stdout only; the audit event already carries the code).

## How to Throw Errors (Backend)

The project uses custom exceptions extending `AppException`. **Never** throw generic `Error` or NestJS `HttpException` directly for known business errors. Use the classes below:

### Exception Classes

| Class | HTTP Status | Usage |
|--------|-------------|-----|
| `AppBusinessException` | 400 | Business rule violations, logical validation. |
| `AppNotFoundException` | 404 | Resource not found (ID missing, route, file). |
| `AppUnauthorizedException` | 401 | Authentication failure (invalid/expired token). |
| `AppForbiddenException` | 403 | Authorization failure (insufficient permissions). |
| `AppConflictException` | 409 | State conflict (email exists, duplicate resource). |
| `AppValidationException` | 422 | Field validation error (DTOs, missing fields). |
| `AppInternalException` | 500 | Unexpected errors, infrastructure failure. |

### Usage Examples

```typescript
import {
  AppNotFoundException,
  AppBusinessException,
  AppValidationException,
  AppInternalException,
  ErrorCode
} from 'src/shared/exceptions';

// Example 1: Resource not found
const user = await this.repo.findOne(id);
if (!user) {
  throw new AppNotFoundException(
    ErrorCode.USER_NOT_FOUND,
    'Usuário não encontrado' // Message in Portuguese
  );
}

// Example 2: Business Error
if (user.isActive) {
  throw new AppBusinessException(
    ErrorCode.USER_ALREADY_EXISTS,
    'Usuário já está ativo'
  );
}

// Example 3: Validation Error (missing field)
if (!mediaInput.fieldKey) {
  throw new AppValidationException(
    ErrorCode.MEDIA_FIELD_MISSING,
    `FieldKey ausente para mídia "${mediaInput.title}"`
  );
}

// Example 4: File not found for upload
const file = filesDict[mediaInput.fieldKey];
if (!file) {
  throw new AppValidationException(
    ErrorCode.MEDIA_FILE_NOT_FOUND,
    `Arquivo não encontrado para upload: ${mediaInput.fieldKey}`
  );
}
```

### Try-Catch Pattern with Transaction

When using database transactions, follow this pattern to properly handle and re-throw exceptions:

```typescript
async createPage(dto: CreatePageDto): Promise<PageEntity> {
  const queryRunner = this.dataSource.createQueryRunner();
  await queryRunner.connect();
  await queryRunner.startTransaction();

  try {
    // Validation that throws custom exceptions
    const existingPage = await this.validatePage(dto.id);

    // Business logic
    const page = await queryRunner.manager.save(PageEntity, dto);

    await queryRunner.commitTransaction();
    return page;
  } catch (error) {
    await queryRunner.rollbackTransaction();
    this.logger.error('Error creating page', error.stack);

    // IMPORTANT: Re-throw if it's already a custom exception
    if (error.code) throw error;

    // Wrap unknown errors in AppInternalException
    throw new AppInternalException(
      ErrorCode.PAGE_CREATE_ERROR,
      'Erro ao criar a página',
      error
    );
  } finally {
    await queryRunner.release();
  }
}
```

**Key Points:**
1. Always check `if (error.code) throw error;` before wrapping - this preserves specific error codes from validation methods
2. Use `error.stack` in logger for proper stack trace
3. Pass the original error as third parameter to `AppInternalException` for debugging

### S3 Operations Error Handling

```typescript
// Delete operation
try {
  await this.awsS3Service.delete(media.url);
} catch (error) {
  this.logger.error(`Failed to delete S3 file: ${media.url}`, error.stack);

    ErrorCode.S3_DELETE_ERROR,
    `Falha ao remover arquivo do S3: ${media.url}`,

  const url = await this.awsS3Service.upload(file);

  );
}
```

## How to Handle Errors (Frontend)

### TypeScript/React Example

```typescript
interface ApiError {
  success: false;
  error: {
    code: string;
    message: string;
    details?: unknown;
    timestamp: string;
    path: string;
  };
}

async function handleApiError(response: Response): Promise<never> {
  const error: ApiError = await response.json();

  // Handle by code
  switch (error.error.code) {
    case 'AUTH_1001':
    case 'AUTH_1002':
    case 'AUTH_1003':
    case 'AUTH_1004':
      // Redirect to login
      window.location.href = '/login';
      break;

    case 'PERM_3001':
    case 'PERM_3002':
      // Show access denied message
      toast.error('You do not have permission for this action');
      break;

    // Handle media validation errors
    case 'MEDIA_8804':
    case 'MEDIA_8805':
      toast.error('Arquivo obrigatório não enviado');
      break;

    default:
      // Show server message (already in Portuguese)
      toast.error(error.error.message);
  }

  throw error;
}

// Usage
try {
  const response = await fetch('/api/users');
  if (!response.ok) {
    await handleApiError(response);
  }
  return response.json();
} catch (error) {
  console.error('API Error:', error);
}
```

### Handling by HTTP Status

| Status | Recommended Action |
|--------|------------------|
| 400 | Show validation message |
| 401 | Redirect to login |
| 403 | Show "Access Denied" |
| 404 | Show "Not Found" |
| 409 | Show conflict (e.g., email already in use) |
| 422 | Show field validation errors |
| 500 | Show "Internal Error, please try again" |

## Form Validation

When the error contains `details` with field information:

```json
{
  "success": false,
  "error": {
    "code": "USER_2003",
    "message": "Este email já está em uso por outro usuário",
    "details": {
      "field": "email"
    },
    "timestamp": "2024-01-15T10:30:00.000Z",
    "path": "/api/users"
  }
}
```

Use `details.field` to highlight the input with error in your form.

## Best Practices

1. **Always check `success`**: If `false`, treat as error.
2. **Use `code` for logic**: More stable than the message string.
3. **Show `message` to user**: It is already provided in Portuguese.
4. **Log `timestamp` and `path`**: Useful for debugging.
5. **Handle network errors**: `catch` for when the request fails completely.
6. **Re-throw custom exceptions**: In catch blocks, check `if (error.code) throw error;` before wrapping.
7. **Log with stack trace**: Use `error.stack` when logging errors.
8. **Never use NestJS built-in exceptions**: Always use custom `App*Exception` classes.

## Technical Implementation Details

### Base Class (AppException)

```typescript
// src/shared/exceptions/base.exception.ts
import { HttpException, HttpStatus } from '@nestjs/common';
import { ErrorCode } from './error-codes.enum';

export class AppException extends HttpException {
  constructor(
    public readonly code: ErrorCode,
    message: string,
    httpStatus: HttpStatus,
    public readonly details?: unknown,
  ) {
    super({ code, message, details }, httpStatus);
  }

  getCode(): ErrorCode {
    return this.code;
  }

  getDetails(): unknown {
    return this.details;
  }
}
```

### GlobalExceptionFilter

The global filter intercepts **all** application exceptions:

```typescript
// src/shared/exceptions/filters/global-exception.filter.ts
@Catch()
export class GlobalExceptionFilter implements ExceptionFilter {
  private readonly logger = new Logger(GlobalExceptionFilter.name);

  catch(exception: unknown, host: ArgumentsHost): void {
    const ctx = host.switchToHttp();
    const response = ctx.getResponse<Response>();
    const request = ctx.getRequest<Request>();

    const errorResponse = this.buildErrorResponse(exception, request);
    const status = this.getHttpStatus(exception);

    // Log with appropriate level
    if (status >= 500) {
      this.logger.error(
        `[${errorResponse.error.code}] ${errorResponse.error.message}`,
        exception instanceof Error ? exception.stack : undefined,
      );
    } else {
      this.logger.warn(
        `[${errorResponse.error.code}] ${errorResponse.error.message} - ${request.method} ${request.url}`,
      );
    }

    response.status(status).json(errorResponse);
  }
}
```

Validações de DTO (`lockVersion` ausente, campos não declarados, limites)
continuam respondendo 400 pelo `ValidationPipe` global. Folhas que não cabem na
página (meditações, trabalho manual), imagens em formato não suportado e assets
obrigatórios sem URL respondem 422 na prévia, exportação e publicação. A fila de
conversão PDF cheia responde 503.

### Falhas de geração (`failureCode` da etapa)

A geração roda em segundo plano; a falha não é uma resposta HTTP. Ela fica em
`failureCode`/`failureMessage` da etapa. Uma etapa que já tinha versão a
preserva e volta ao status anterior ao pedido; sem versão anterior, vai a `FAILED`.

| `failureCode` | Significado |
| --- | --- |
| `GENERATION_REQUEST_MISSING` | Geração interrompida sem dados para retomada |
| `GENERATION_ATTEMPTS_EXHAUSTED` | As 3 tentativas do pedido foram consumidas |
| `UPSTREAM_CHANGED` | O conteúdo dos itens anteriores mudou durante a geração; uploads não confirmados são removidos |
| `AI_INCOMPLETE_RESPONSE` | Resposta cortada (OpenAI `incomplete_details`, Gemini `MAX_TOKENS`) ou narrativa com sinais formais de corte |
| `AI_CONTENT_INVALID` | Conteúdo reprovado na validação local ou na revisão, após as correções permitidas |
| `AI_IMAGE_INVALID` | Imagem do provedor fora de PNG/JPEG ou acima de 15 MiB |
| `AI_CONFIGURATION_MISSING` | Chave de API ausente ou ilegível para o provedor selecionado |
| `AI_CONNECTION_INTERRUPTED` | Queda de conexão persistente ao gerar imagem |
| `AI_QUEUE_UNAVAILABLE` | Fila de IA indisponível, cancelada ou interrompida |
| `AI_QUEUE_TIMEOUT` | Tempo de espera da fila de IA excedido |
| `AI_BILLING_INACTIVE` | Faturamento inativo no provedor |
| `AI_CREDITS_EXHAUSTED` | Créditos esgotados |
| `AI_USAGE_LIMIT_EXCEEDED` | Limite de gasto/uso da organização ou projeto |
| `AI_QUOTA_UNAVAILABLE` | Cota insuficiente |

O provedor citado na mensagem vem do snapshot da tentativa, não do texto do
erro. Não se salva conteúdo parcial nem se completam frases automaticamente.
Revisão ausente ou malformada do item 7 não equivale a aprovação. Uma falha de
renderização em qualquer PDF durante a publicação não cria material e devolve a
lição a `READY_FOR_PUBLICATION`.

## Clubinho media submissions

`POST/PATCH /image-sections` validate the exclusive photo/video selection before
writing files. `VALIDATION_ERROR` rejects empty, mixed, excessive or unsupported
collections; `INVALID_INPUT` rejects foreign/repeated media IDs, media-type
changes, unsafe photo links, or new video links; `INVALID_FILE` rejects
MIME/extension/signature/size mismatches, duplicate file bindings and unmatched
files. `MEDIA_FILE_NOT_FOUND` identifies an upload without its file. DTO
validation rejects caller-provided authorship and visibility on create.
Multer also bounds multipart file count (20) and per-file bytes (100 MB).

Video comments use the existing comment errors and moderation rules. MEDIA_NOT_FOUND
still rejects unsupported media, media outside the configured feed and private
anonymous access; VIDEO is now an allowed media type alongside IMAGE.

## Shared idea media and AI review

New shared-idea media validation returns `400` with the existing error envelope and `VALIDATION_ERROR`, `INVALID_INPUT`, `INVALID_FILE` or `MEDIA_FILE_NOT_FOUND`. Other modules keep their existing `AppValidationException` default (`422`). Multipart limits may fail earlier in Multer.

| Code | HTTP | Meaning |
| --- | --- | --- |
| `IDEA_AI_8620` | 409 | An attempt is active; wait or explicitly publish the original |
| `IDEA_AI_8621` | 409 | Three-attempt limit reached |
| `IDEA_AI_8622` | 409 | Choices refer to an obsolete enhancement |
| `VALIDATION_ERROR` | 422 | An AI publication choice has no available approved result |

Worker errors are sanitized `errorCode` values on attempts, not failed submission responses: `PROVIDER_NOT_CONFIGURED`, `PROVIDER_REQUEST_FAILED`, `INVALID_PROVIDER_RESPONSE`, `GUARD_REJECTED`, `LIMIT_REACHED`, `CANCELLED`. The teacher's persisted submission and the previous successful result remain available. See [shared idea enhancement](api-ideas-enhancement.md).

## Fila de requisições de IA (AI_QUEUE_92xx)

`AI_QUEUE_9201` (`AI_QUEUE_UNAVAILABLE`) representa falhas da própria fila ou do
transporte, nunca uma resposta do provedor. O status é 503, ou 400 para um
pedido interno inválido. `details.reason` traz um dos identificadores abaixo;
URLs do Redis, credenciais e mensagens brutas do provedor nunca são devolvidos.

| `details.reason` | Significado |
| --- | --- |
| `AI_QUEUE_UNAVAILABLE` | Redis ou fila indisponível |
| `AI_QUEUE_EXPIRED` | Prazo do pedido vencido antes de chegar ao provedor |
| `AI_QUEUE_CANCELLED` | Pedido cancelado pelo produtor |
| `AI_QUEUE_INVALID_REQUEST` | Destino ou formato não permitido (400) |
| `AI_QUEUE_RESULT_EXPIRED` | Resultado expirou antes de ser consumido |
| `AI_QUEUE_ORPHANED` | O processo que enfileirou o pedido não existe mais |
| `AI_QUEUE_CREDENTIAL_MISSING` | Provedor sem chave de API legível |

No Estúdio, essas falhas viram `AI_QUEUE_UNAVAILABLE`, `AI_QUEUE_TIMEOUT` ou
`AI_CONFIGURATION_MISSING` na etapa. Os jobs de ideias compartilhadas mantêm o
contrato de tentativa com falha; o catálogo de modelos mantém a lista de
contingência. Ver [comportamento da fila](ai-request-queue.md).
