## Intended outcome and invariants

1. Manual editing, subsequent generation and PDF export agree on the same canonical content/version.
2. Completion, approval and return-for-changes apply to the stage lock observed by the actor.
3. Generated assets remain readable while referenced by any preserved version or publication. Deletion never trusts arbitrary JSON strings as proof of ownership.
4. Generation and publication have explicit ownership, bounded work and recoverable terminal states. A stale worker cannot commit.
5. A successfully published lesson maps to one weekly material; process failure cannot require blindly creating another page.
6. Authenticated admin checks, public error envelopes, current editorial contracts and the distinction between publication/current-week selection remain intact.

These are implementation targets. No new tables, fields, endpoints, queues or external secret services described below already exist by implication.

## BE01 — make image retrieval a controlled boundary

Files: [asset-url.utils.ts](../../src/modules/ai-lessons/utils/asset-url.utils.ts), [docx-exporter.service.ts](../../src/modules/ai-lessons/services/docx-exporter.service.ts), relevant provider interfaces and asset tests.

Implementation:

1. Introduce an injectable asset reader. Prefer server-owned object identifiers in the configured S3 bucket for generated images; do not accept arbitrary storage keys from content requests.
2. Inventory legacy URL shapes with read-only fixtures before restricting accepted hosts. Reuse the existing configured bucket rules; do not hardcode a bucket, region or production domain.
3. For any external URL support that remains, normalize IPv6 correctly, reject loopback/private/link-local/unspecified/mapped destinations, validate DNS results and bind the connection to validated addresses. Avoid a separate preflight lookup followed by an unvalidated second resolution.
4. Disable redirects by default or validate every destination under the same policy. Restrict protocols, credentials in URLs, allowed ports and response size/type.
5. Enforce byte limits while reading, including decompression behavior, and verify image signatures before constructing the DOCX. Keep timeout behavior explicit.
6. Preserve safe public errors and internal diagnostics without embedding response contents or credentials.

Acceptance:

- The reproduced IPv6 URLs are rejected before a network request.
- A public hostname resolving privately, an IPv4-mapped IPv6 destination and a redirect to metadata/loopback are rejected in deterministic transport tests.
- Authorized existing PNG/JPEG assets remain exportable; oversized or non-image responses fail with a documented client-safe error.
- No arbitrary local path or unrestricted URL is passed to the exporter.

Tests: expand `asset-url.utils.spec.ts`; add downloader tests with mocked DNS/HTTP/S3. No live metadata request or external fetch is needed. Browser-visible errors are coordinated with FE02/FE08.

## BE02 — preserve Studio assets during deletion and maintenance

Files: [audit-orphans.js](../../scripts/s3/audit-orphans.js), `LessonDraftService.generateAndStoreAssets/delete`, `lesson-version.entity.ts`, existing media tracker/processor utilities and S3 provider.

Immediate non-schema correction:

- Make the orphan inventory include `media_items` plus every retained lesson version's asset references and document keys. Scan current and historical versions; currentVersionId alone is insufficient.
- If any reference source cannot be read or parsed reliably, stop destructive cleanup. Do not interpret an unavailable table/source as an empty reference set.
- Protect uploads in flight. Until an authoritative upload ledger exists, do not classify potential Studio uploads as destructively removable merely because no committed version references them yet.
- Keep dry-run as default and show which reference source protects an object. Preserve the script's explicit delete/confirm requirement; do not run deletion in this task.
- Add tests that execute the inventory/deletion decision with synthetic clients, including the reproduced asset-known-only-to-lesson-versions case.

Ownership follow-up:

1. Replace deletion decisions based on recursive string extraction with server-established ownership/reference records. Reuse existing media infrastructure only if it can represent retained versions and active uploads without weakening its target semantics.
2. If it cannot, introduce a minimal Studio asset ledger through entity changes and a generated migration. Required information is object identity, producing attempt/lesson, state and references; finalize the entity shape in this package's design commit.
3. Register successful uploads durably before treating them as disposable. A crash must leave enough metadata for conservative reconciliation.
4. On lesson deletion, delete only owned objects with no remaining reference. URLs in arbitrary notes or an object shared by another lesson/material must not be deleted.
5. Preserve the S3 provider's current behavior of logging ordinary delete failures without failing the already-completed database deletion. Add durable retry/reconciliation where justified; logs alone are not an ownership registry.

Acceptance: the existing auditor never schedules a valid Studio image for deletion; shared/foreign objects survive lesson deletion; in-flight/recently committed assets survive a concurrent audit; unavailable reference storage fails closed. Cleanup of an actual unreferenced owned asset remains possible and auditable.

Compatibility: do not remove legacy URLs or rewrite all historical versions automatically. Inventory/backfill must report ambiguous ownership and retain those objects. A data-repair operation is separate from an automatically generated schema migration.

## BE03 — reconcile manual documents into canonical content

Files: `services/lesson-draft.service.ts`, `utils.ts`, meditation content adapters, `docx-exporter.service.ts`, DTOs/types and fixtures. Extract an operation-focused update service as this responsibility moves out of the large orchestrator.

Implementation:

1. Define typed per-stage adapters with a single rule: a saved document's edited fields are authoritative; non-editable assets/provider metadata stay server-owned.
2. For the lesson, synchronize narrative, memory verse/reference/version, purpose, songs, application, counseling and questions where editable. Explicitly represent an emptied field; do not use truthiness to restore its previous value.
3. Add stable document field attributes for new documents and deterministic legacy-heading support. Ambiguous/missing legacy structure must produce actionable diagnostics, not invented content.
4. Apply the existing meditation adapters consistently at save and export, preserving rich text, native grids and internal answers. Do not expose teacher answers in child-facing documents.
5. For games, derive steps/captions from the same edited representation. Detect image-to-step count/source mismatches and require correction/review before completion. Do not automatically spend on image regeneration or silently reuse an image as a different step.
6. Preserve asset identity and other server metadata rather than accepting a complete client replacement of arbitrary structured data. Coordinate legacy API consumers through explicit DTO mapping.
7. Compute checksums from the canonical semantic representation used for dependency checks. Keep deterministic ordering and preserve the current downstream invalidation policy.
8. Validate essential completeness before production completion and publication. A safe partial draft may be saved, but it must not become an approved blank/malformed product.

Acceptance:

- Changing verse/application changes the source supplied to derived generators and matches lesson PDF text.
- Deleting narrative does not silently restore its previous content; completion fails until required content is repaired.
- Multi-story headings, editor formatting and historical documents remain readable.
- Game text and visual captions agree; image identity is not changed by a text-only edit.
- Preview and final export use the same version and adapter semantics for all eight stages.

Tests: fixtures covering original generation, manual edits, erased fields, legacy ASTs, structured-only fallback, rich text and invalid structures. Mock LLM calls and inspect their inputs. Inspect native DOCX XML; perform separate real LibreOffice rendering with local fixtures when implementation changes the renderer. Semantic/Biblical correctness still requires human review.

## BE04 — enforce the observed version and global busy state

Files: `generate-stage-request.dto.ts`, controller, workflow services/repository, response/error contracts, corresponding frontend types.

Proposed API change: require the existing stage `lockVersion` in completion, approval and request-changes requests. It is not currently required by those endpoints. Compare it under the same lesson transaction/lock used to change state. No additional version column is required for this protection.

Implementation:

- Validate lesson/stage existence, aggregate state, stage state, content availability and observed lock before writing.
- Apply generation/publication exclusion consistently to save, completion and relevant review mutations. An old browser must not invalidate a paid active generation through a different endpoint.
- Return the established 409 envelope with a specific, documented conflict reason. Do not retry stale review mutations automatically.
- Preserve current semantics: remaining `IN_REVIEW` items can be reviewed when the package is `CHANGES_REQUESTED`; resubmission changes producer-approved items as currently designed.
- Bind preview to the reviewed version through an explicit precondition or version selection contract. Define whether a changed preview target returns conflict or serves that immutable historical version; recommended first delivery is conflict against the current stage lock.

Acceptance: stale completion/approval/devolution is rejected; exactly one of concurrent incompatible actions succeeds; no comment/approval write occurs after a failed precondition. Saving upstream during another active generation receives conflict instead of turning that job STALE.

Rollout: current global validation rejects unknown fields. First deploy additive DTO support, then FE03 sending locks, then enforce mandatory preconditions after old clients are retired or use a separately versioned action contract. Do not describe the transitional permissive phase as fully fixed. Test old/new combinations explicitly.

Tests: service concurrency interleavings, repository conditional/lock assertions and Nest/Supertest status/DTO/guard tests with mocks. Validate actual SQL/lock behavior separately on an isolated local database under the repository's database workflow; unit mocks cannot establish transaction isolation.

## BE05 — make publication recoverable and uniquely linked

Files: `LessonDraftService.publishToWeekMaterial`, `lesson.entity.ts`, repositories, `WeekMaterialsPageCreateService`/entity, scheduled recovery wiring and publication DTOs.

Recommended design, to be implemented additively:

1. Persist a publication attempt owner/lease and the exact eight approved version IDs reserved for that attempt. Add focused fields to the existing aggregate unless a separate operation entity is demonstrably needed; do not require a general-purpose queue platform for this correction.
2. Add a nullable unique origin link on weekly material, such as `sourceLessonId`, and create/reconcile by that database-enforced key. This field is proposed and does not exist today.
3. Generate all PDFs from the reserved immutable versions. Avoid eight independent full-history reloads whose results are not tied to that reservation.
4. Renew publication ownership during long work. Expired ownership permits recovery only after checking whether the material already exists.
5. If material exists, reconcile the lesson link; if it does not, safely resume/restart rendering under a new owner. A stale worker cannot finalize after takeover.
6. Recover on startup and periodically. Distinguish active publication, recoverable failure and completed result in the documented response. The existing synchronous endpoint can remain initially; 202/operation endpoints are optional later changes, not prerequisites assumed by this plan.
7. Prevent duplicate page/media/notification creation through the origin key and transaction boundary. Never promise exactly-once external processing or billing.
8. Replace description-marker lookup as the primary identity guarantee. Legacy marker fallback is allowed only for an unambiguous match; report multiple/conflicting matches rather than selecting the first result.
9. Preserve already-published materials, their links and the existing eight-file naming contract. Do not silently republish or mark a different week as current.

Failure matrix / acceptance:

| Failure boundary | Required outcome after restart/retry |
| --- | --- |
| After reservation, before first PDF | Recover without indefinite PUBLISHING |
| During any of eight renders | No partial weekly page; recoverable error or safe retry |
| During upload/page transaction | Reconcile partial external work conservatively |
| After page commit, before lesson link | Discover the unique origin and attach that same page |
| After success, before HTTP response | Repetition returns the same material ID |
| Old worker completes after lease takeover | No stale finalization or duplicate page |
| Existing legacy marker is ambiguous | No automatic duplicate creation or arbitrary attachment |

Schema/rollout: generate migrations from registered entities with the official CLI; use additive nullable fields first. Existing records need a separate idempotent, inspectable reconciliation/backfill design. Do not manually edit generated migrations. Keep schema on application rollback until compatibility is proven; dropping recovery/origin fields is not a safe default rollback.

The weekly-material service also creates routes/media and schedules notifications. Inspect its transaction/compensation paths in this package; do not assume changing the Studio service alone makes all external effects atomic.

## BE06 — make prompt saves/resets atomic

Files: prompt service/repository/entity, `admin-lesson-prompt.dto.ts`, controller and FE01 adapter.

Implementation:

1. Replace read/check/save with an atomic conditional update by admin, stage and observed `lockVersion`; exactly one matching update succeeds.
2. Initial creation uses the existing unique `(adminId, stage)` constraint and maps a concurrent insert to a 409 conflict.
3. Reset requires the observed lock and preserves a monotonically versioned row. Recommended non-schema approach: store an empty custom prompt, expose it as `customPrompt: null`, and keep composing only the official base. Do not delete/reset the version counter.
4. Distinguish initial absence, empty customization and stale expected version in DTOs and service logic.
5. Retain server composition of immutable base + complementary prompt. FE01 sends only the complement; the server must not infer/truncate user instructions.

Acceptance: two writes with the same observed version produce one success and one conflict; reset cannot erase a later save; a stale post-reset save fails; repeated UI saves add the base once; the official lesson base can exceed 12,000 characters without invalidating a short customization.

Tests: concurrent reads/writes with repository-level conditional-update assertions, reset/save interleavings, absent-row insert conflict and FE/API composition contract. Existing nominal 100% service coverage is not sufficient for these scenarios.

## BE07 — freeze attempt inputs and bound expensive work

Files: `configured-lesson-llm.provider.ts`, generation orchestration, stage/version entities, configuration services, provider contract, PDF conversion service.

Implementation sequence:

- Resolve provider, model, template and effective prompt once per attempt. Pass a stable provider context through generation, correction and image calls.
- For restart recovery, persist an immutable non-secret configuration revision/input snapshot. Reference credentials through a controlled runtime mechanism; never copy an API key into the job JSON or public DTO.
- Record actual provider/model, fallback use, attempt ID, duration, safe vendor response IDs and usage when returned. Remove misleading OpenAI-only labels for Gemini operations.
- Observe lease renewal outcomes; stop committing after ownership loss. Provider cancellation is best effort and does not imply cancellation of external billing.
- Add bounded concurrent generation/conversion work. For multiple API replicas, a per-process Set alone is not a global limit; capacity claims must use the chosen shared coordination mechanism.
- Make limits explicit configuration, test them using synthetic capacity values and measure realistic latency before choosing production defaults.
- Introduce image checkpoints only with BE02 ownership/cleanup support. Preserve completed valid images after restart where possible, without mixing input snapshots.
- Preserve existing bounded correction/retry policies; add retry metrics and honor provider-specific transient/permanent distinctions. Do not retry mutations or ambiguous provider timeouts merely because the HTTP client failed.

Acceptance: configuration edits during a job do not mix providers/models; a recovered attempt has defined input identity; stale workers cannot finalize; capacity C never admits more than C work units in the tested coordination scope. Tests must distinguish successful DB idempotency from unavoidable uncertainty about provider billing.

No prices, production quotas or time SLAs are assumed. Secret rotation and any external infrastructure setup require their own concrete implementation work and deployment scope.

## BE08 — reduce detail/event cost without deleting history

Files: lessons controller/repository/response DTOs, event serialization, FE06 transport.

Implementation:

1. Measure response bytes, version/comment counts, query count and serialization time for deterministic small/large fixtures.
2. Add a compact current-state read path using current versions only. Preserve the existing full response during transition; a proposed optional query mode must be documented before clients use it.
3. Avoid sending unchanged snapshots; emit lightweight heartbeats so the client can distinguish idle from disconnected. Define ordering/change identity from all visible fields, not just aggregate `updatedAt`.
4. Bound connection lifetime and resource usage; do not rely on the client's consumed offset to release XHR response memory.
5. Keep JWT/admin protection and response DTO redaction on every variant. Do not expose generation requests, secret config or private fields while optimizing.
6. If history becomes a product surface, provide explicit pagination/selection instead of putting all history back into each event. No history endpoint is assumed to exist today.

Acceptance: identical idle snapshots are not retransmitted indefinitely; changes and terminal states arrive; large-history lessons do not multiply interactive payload size linearly with old versions. Compare measured bytes/queries/memory with the baseline. Preserve SSE cancellation, EOF, refresh and final-denial semantics in FE06.

## BE09 — catalog provenance and credentials

Files: provider controllers/services/DTOs/repository and FE08 provider adapters.

Immediate work:

- Add explicit model-catalog provenance/availability metadata, or return an actionable upstream error while retaining defaults as a separately labeled fallback. Use an enum defined in dedicated types/constants.
- Label the current Gemini catalog as static unless a real provider lookup is implemented. Do not claim fallback entries are available to the active credential.
- Remove/deprecate `apiKey` query transport from the legacy model endpoint. Current frontend uses saved configuration, so inventory other consumers before removal.
- Validate bounded model/config strings and finite provider options; distinguish omitted values from unsupported null. Preserve explicit empty-key removal.

Follow-up security design:

- Move persisted secrets toward a secret reference or application encryption with rotation/versioning. Preserve public `hasApiKey` behavior and avoid environment fallback that would contradict the current DB-managed configuration contract.
- Establish the available key-management mechanism before implementation; this plan does not assume a connected secret manager or authorize infrastructure changes.
- Do not rewrite/delete existing credentials without a verified migration and rollback path. No real credential is needed in tests.

Acceptance: upstream catalog failure cannot be indistinguishable from live success; public responses/logs omit credentials; preserve/replace/remove flows stay compatible; null and over-limit inputs receive validation errors instead of `.trim()` failures.
